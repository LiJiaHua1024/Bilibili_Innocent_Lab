# NPatch 当前实施路线图

更新时间：2026-10-22。实施分支：`feat/npatch-compat`；起点 `2ef9877f`。

本文是兼容性总览与 Feature Program 合并后的唯一当前排期入口。原文保留为[兼容性调研与验收档案](npatch-compatibility-plan.md)及[Feature 可行性研究](npatch-feature-program.md)，其中历史“现状”、勾选框、工期与阶段编号不再表示当前进度。这里的“待做”表示已纳入路线，“探索”表示尚未承诺实现。

## embed 正式支持目标

2026-10-21 用户明确要求正式支持 embed，并推进完整增强。embed 作为与 Manager 并列的支持模式，后续覆盖现有模块功能、实际宿主使用流程及完整安装/升级/恢复/诊断链路。原 F10 的“最小闭环”只代表基础设施阶段，不再作为 embed 的最终交付目标。

原阶段 2 更名为 **2A 基础闭环**，已提交为 `ed529619`；2A 的 `:web` 整进程功能隔离属于临时措施。本轮 2B.1 已定位到 833 原生 loader 的 TLS 析构注册与 linker/path 锁反转，修复 loader 后解除隔离，保留原 Hook 注册时序；验证结果见文末。**2B 正式支持** 是当前主线，在完成正式准入前保持实验性标识，不把 2A 或 Web 单项结果表述为 embed 全功能验收完成。阶段 3–6 的通用增强同时覆盖 Manager/embed，不能只给 Manager 实现后把 embed 留在基础闭环。


## 2026-10-22 范围校正与当前下一步

用户明确本分支是 NPatch 专项；“全面支持 embed”要求完整支持该加载模式，不要求修好全部宿主业务功能。此前把 410 行逐项行为验收全部完成设为进入 2B.3 的前置条件，范围过大，现已废止。以下历史记录保留事实，但其中“继续逐项修复”“全量矩阵完成后再进入 2B.3”等排期不再有效。

- 已完成的 Web loader、直连配置、授权、多进程、账号/下载及各类别行为证据复用，不重复测试、不撤销已提交修复。
- 立即进入 **2B.3：内嵌模块与设置 App 的构建/协议一致性、同版本码不同内容、重新修补、安装升级与恢复**，随后补齐专项代表性回归和正式准入。
- 结束页空标题通用修复已保存至 `captures/npatch-2b/deferred-end-page/` 的可恢复补丁及新增文件副本，从当前源码移出，不纳入专项提交；初步证据保存在 `captures/npatch-2b/end-page-acceptance/`，两行矩阵继续 pending。
- 标签/课程正样本、其它普通过滤条件、通用控件适配等作为模块业务待办记录；没有 embed 差异证据时不继续沿此方向自动修复。外观等尚缺的类别只补代表性兼容路径。
- 阶段 3–6 仍保留原 NPatch 专项增强排期，不能再被通用模块缺陷清单无限推迟；embed 正式准入不等同于这些后续增强全部完成。

## 已完成的基线

B1–B12 已按范围闭环，详见[专项验收结论](npatch-compatibility-plan.md#2026-10-20-专项验收结论)：

- 免 Root 关闭门控与关闭确认、重复/乱序回执、Manager 不可达分类、诊断徽章和预期日志短路已修复（覆盖 F1–F4 的主要缺陷）。
- 有序广播无人处理时结束空等；默认 Manager 补丁已验证 `:download` / `:ijkservice` 注入。
- 833 loader 的 Manager 失联问题已有固定输入哈希、单方法修补工具，需重新修补宿主，不能仅更新模块解决。
- 冷启动已做对照归因：约 11 秒宿主/环境基础耗时仍在；正常开启额外约 2 秒 Hook 链，授权约几十毫秒。归因完成不等于优化完成。
- 上轮通过 Debug/AndroidTest APK、3651 项 JVM 测试（0 失败、1 跳过）、3 项实机 IPC 回归与快速 Lint；这些是上轮证据，不冒充后续源码的检查结果。

## 阶段 2B：embed 完整功能与正式准入

以下按实施顺序执行。正式支持以公开声明的版本/系统/ABI 范围为边界，矩阵外维持未知；当前 8.90.2/833/Android 16/arm64 的证据不能代替其它组合。

1. **Web 根因与功能恢复**。已定位并修复 833 原生 loader 的 linker/path 锁反转，删除 `NPatchProcessFeaturePolicy` 的临时整进程隔离。无需延迟或跳过原有公共 Hook；关闭或条款拒绝时也会经过 loader，必须一并回归。验收覆盖首次及重复打开网页、返回/关闭、分享、后台恢复、冷启动、条款拒绝和免 Root 关闭。保留 ANR 线程栈、旧实现稳定复现及修复版回归，产物固定输入并校验双 ABI native 哈希；具体结果见文末。
2. **功能通道与进程兼容对齐**。目录矩阵继续用于防遗漏和保存已有证据，不以 410 行逐项行为通过作为 embed 准入门槛。覆盖净化/过滤、评论/复制、播放器、外观、账号授权和 native 等功能类别的代表性回归，以及主进程、Web、下载/播放服务的实际业务路径；核对无 embed 专用功能裁剪、配置/授权可达、适配数据源正确、开关生效和必要组合。异常先归因：有模式对照或 loader/协议/进程/构建来源证据的 NPatch/embed 差异在本分支修复；通用宿主适配或原有业务缺陷单独记录，不自动修复、不作为专项发布阻塞。未经对照的异常保持待归因，不宣称是 embed 引入，也不据此扩大到全面代码审查。需要账号的路径使用已授权测试账号。功能安装数量和全局心跳不能代替代表性行为证据。
3. **完整安装、更新与恢复**。完善无 Manager 的模式识别、首次引导、配置变更和重启引导；验证全新安装、保留数据升级、重新修补、Manager/embed 切换、设置 App 停止/升级/重装、条款撤回与配置恢复。加入内嵌模块与独立设置 App 的构建/协议一致性检查，覆盖“版本码相同但 APK 内容不同”，提供明确的重新修补路径。修补工具从固定 Debug 测试输入扩展到可维护的发布产物、用户签名及同证书升级流程，避免输出或记录私钥/口令。固定作用域与模块更新需重新修补等加载方式约束，需在正式流程中清楚引导。
4. **兼容边界和必要增强**。将阶段 3 的 embed 签名/ABI/native/适配缓存准入项及阶段 4、6 中阻断正常使用的诊断、漂移检查、恢复和引导提前纳入 2B。测试登录、播放、下载、WebView、分享与账号风控，核查原 dex 来源及缓存失效。833 embed 当前签名等级上限 2、无热重载等上游限制要有源码证据；若限制阻断核心功能，评估可维护的 loader/patcher 修复或替代路径并验证，不能只记为“Manager 独有”后结束。无法等价实现的能力需逐项说明客观原因、用户影响和可用替代，不得把未研究/未测试列为永久限制。
5. **正式发布验收**。声明并冻结首个支持矩阵，对范围内功能通道和类别完成代表性兼容回归，并关闭所有已确认的 embed 专属阻塞，验证安装/升级/配置/关闭/恢复及异常路径，并回归 Manager 与标准框架。普通迭代仍按既有 FastLint 规则；到正式发布验收时执行完整 Lint、Release/R8 和对应测试。形成可复现产物、参数与签名说明、支持文档及问题定位材料，验收完成后才移除实验性标识。本轮设备授权仍只覆盖有线备用机，标准框架实机回归使用另行可用且已授权的环境。

2B 退出条件：embed 无人为功能裁剪，功能类别和适用进程的代表性兼容回归通过；已确认的 NPatch/embed 加载、配置、授权、ABI/适配来源差异闭环；必要安装升级恢复链路、构建/协议一致性、明确的重新修补引导及正式发布门禁通过。支持范围、未测组合与客观限制如实说明。全量目录中 pending 的通用业务条目不等同于 embed 缺陷，不要求在此分支消灭模块所有既有问题。已取得的逐项证据继续保留，未测项不伪装通过；用户后续要求的独立通用修复另行安排。

## 过时或撤回的方案

| 原方案/判断 | 当前处理 |
|---|---|
| F6：缓存许可直接安装，后台再授权；不可达时继续采用许可快照 | 撤回。缓存无法证明用户之后未关闭；NPatch 必须取得当前端点许可，端点全部不可达时不安装功能 Hook |
| 冷启动总是被固定 2 秒 admission 阻塞 | 历史现象。B11 已解决无人处理后的空等；当前应测量真实 Hook 链，不能照搬旧性能目标 |

| 子进程统一要求 `--injectdex` | 已纠正。默认 Manager 已验证普通子进程注入，其它进程和功能分别验收 |
| 副用户/工作资料可隔离同包名不同签名宿主 | 不可行。包安装设备级共享，采用有线备用机 |
| F10/embed 放到所有体验功能之后 | 被本路线取代。它属于原总览的主要兼容目标，在配置自主化后实施 |
| F10 最小闭环或临时 `:web` 隔离通过，即表示 embed 工作结束 | 被用户正式支持目标取代。2A 只完成基础设施，2B 是必做主线，需修复根因并逐功能验收 |
| 延迟自由复制共用 Hook 到 `Application.onCreate`，作为 Web 根因修复 | 撤回。该候选开启态能渲染，但条款拒绝、功能 Hook 为 0 时仍出现原生死锁。最终修复 TLS buffer，不改变 Hook 时序 |
| 热重载可实现全部设置免重启；全屏冻结用于修复闪退 | 不成立。热重载与 Hook 生命周期不匹配；冻结只能作为有证据的负载优化 |
| 研究文档建议提高 NPatch 版本即可直接执行 | 版本与在线状态未核实；不根据历史猜测升级依赖或替换框架 |

## 本轮验证记录

### 2026-10-21 阶段 1 验收

环境：唯一有线设备 `13a7a291`，Android 16、arm64-v8a，B 站 8.90.2（8902100），Manager 1.0.9（833），补丁档案为 Manager 模式、签名等级 2、Loader 833/API 102。模块为本分支 1.2.0 Debug（版本码 21）。设备原有模块版本码 22 且签名不同，按用户本轮明确授权卸载模块及测试包后安装本分支产物，并重新添加 Manager 作用域；没有卸载 B 站，也没有操作无线机。

验证结果：

- 最终一次固定源码/资源的 `assembleDebug assembleDebugAndroidTest testDebugUnitTest lintFast` 成功，3660 项 JVM 测试，0 失败、1 跳过；快速 Lint 250 条警告，原 3 条错误基线保持不变。Gradle/Kotlin 守护进程已退出。期间有一次本地化检查碰到编辑中的新旧资源名，已在资源收敛后重新运行通过，不沿用该次失败结果。
- `NPatchDirectPublicationInstrumentedTest` 6 项通过：不依赖兼容开关/远端同步的正 revision 文档、单次租约、设置变化与条款撤回使许可失效、停用门控、模块 UID 不得冒充宿主、纯本地重启落盘屏障。这是端点/持久化契约检查，不冒充真实宿主 IPC。
- `HostAdmissionFallbackInstrumentedTest` 4 项通过：NPatch 不采用旧标准文档/旧正 revision 缓存；无 Manager 文档仍须取得当前许可；标准框架保留已校验文档回退。
- `NPatchDirectHostInstrumentedTest` 真实宿主全过程通过（71.58 秒）：临时停用 Manager 包，关闭通信兼容模式；冷启动取得 `module_direct` 许可并完成 Hook 安装；修改配置后再次冷启动，精确匹配新发布身份；关闭后不安装 Hook，当前拒绝及探测回执确认停用；重新开启再次完成直达安装。该测试会改变测试配置并重启宿主，仅按专项需要显式运行。

### 2026-10-21 阶段 2B.1：Web 原生死锁修复

本节更新当前状态，上述 2A 的 `GATED` 表格只保留为历史对照。用户要求先完成无需账号的部分；登录、下载及账号授权流程仍为待验，不作为本轮阻塞，也不记为通过。

**根因已定位**：833 原生 `bypass_sig.cpp` 在持有 `g_path_mutex` 时首次使用 `thread_local std::string`，通过 `__cxa_thread_atexit_impl` 注册 TLS 析构函数并等待 linker 锁；另一线程在 `dlopen` 持有 linker 锁时进入文件重定向，等待路径锁，形成 AB-BA 死锁。实际 ANR 是 `:web` 的 SmallAppService 启动超时，主线程等待 Gripper；相关线程同时卡在 TLS 析构注册、文件重定向和 nativeLoad/dladdr。原始 833 库相应 PC 的反汇编确认调用了 `__cxa_thread_atexit_impl`。证据：`captures/npatch-2b/accepted/terms-anr-traces.txt` 与 `captures/npatch-2b/libnpatch-833.so`。
